## 二、组 1：低风险体检项（建议本轮，单独一版）

### A. 静默失败定向盘点（承接 FIX-06 的同一类）

- **现状**：`lib/` 内 `catch (_) {` 形态 **313 处**（插件目录 `server_ops` 9 处、`novel/core` 10 处最密），
  其中只有约 **95 处**（30%）后面跟了说明理由的注释。
- **机制**：真出问题的是**子集** —— "捕获了异常、但调用方据此告诉用户成功"的那类（FIX-06 的
  `_persist()` 就是原型：落盘失败却提示成功）。全量翻 313 处不值当，判据要窄。
- **改动**：只扫**写操作 + 网络传输 + 持久化**三类路径里的空 catch，逐条判"失败时用户看到什么"；
  该改的按 FIX-06 三件套（返回 bool + 可查标志 + 落 AppLogger；读盘损坏先备份 `.corrupt.<ts>`）。
- **收益**：把"看起来成功"的失败面收掉 —— 本轮三次真 bug 里有两次属于这一类。
- **成本**：0.5–1 天。
- **验收**：每条改动配"控制组"用例（先断言前提存在，再断言失败可见）；CI 数字回落基线。

### B. 备份盲区：图片平台状态与旧 APK

- **现状**：`/home/update-server/backups/` 每天 03:20 有 `app.db` 的 gz 备份 ✅（实测今天的在）。
  但**没有**备份：
  - `/opt/box-backend/data/image-platform-state.json`（**10 MB**，图片平台全部账户/配额/题库状态）
  - `/home/update-server/public/updates/`（**1.1 G**）—— 旧版本 APK，**回滚要用**，删了就再造不出来
- **机制**：这两样丢一次就是**不可逆**的：state 丢了配额与题库全没；旧 APK 丢了没法回滚，
  只能让用户重新装新版。它们恰好都不在那条已有的备份任务里。
- **改动**：扩一条每日备份（state JSON 带 gzip + 保留 N 天；旧 APK 只做清单/校验和留档，
  或者按版本保留最近 K 个），并做**恢复演练**（从备份还原到一个临时目录并校验 JSON 可解析）。
- **收益**：把唯一一类"不可逆损失"关掉。
- **成本**：0.5 天（含一次恢复演练）。
- **验收**：备份产物带时间戳、`gzip -t` 通过、`python3 -m json.tool` 可解析；演练记录写进文档。

### C. 陈旧备份清理（顺手）

- **现状**：`/opt/box-backend/data/` 下有 **7 个** 陈旧 `*.bak*`（合计 **27 MB**，最早 6 月），
  其中 `image-platform-state.json.bak-purge-*` 等已无引用。
- **改动**：保留最近 2 个，其余删除（先列清单再删）。
- **成本**：10 分钟。**验收**：目录里 `.bak*` 计数 = 2。

### D. 巡检脚本的真机自检（唯一没跑过的告警链）

- **现状**：本轮已把三条告警/监控链在真机证明（磁盘 🟡、资源 🔴→🟢 都真发出来了）。
  `security-patrol.py --test` **还没在真机跑过**（它的投递路径修过但没自证）。
- **改动**：`env -i PATH=/usr/bin:/bin HOME=/root /usr/local/sbin/security-patrol.py --test` 跑一次，
  确认飞书收到。
- **成本**：10 分钟。**验收**：飞书收到那条自检。

## 三、组 2：投稿 → 审核 → 上架，**首次端到端跑通**（建议单独一版）

- **现状**：链路两端都在，但**从未一起跑过**：
  - App 侧：`lib/features/extensions/market/presentation/plugin_submit_page.dart`（投稿页，支持表单 / zip）
  - 服务端：`tool/image_platform_quota_server.dart:465` 起 —— `GET /api/plugin-market`、
    `POST /api/plugins/submissions`、`POST /api/plugins/submissions/zip`、
    `GET /api/plugin-market/<id>/package`、`POST /api/plugin-market/status` 都在
  - 证据：线上清单**只有 136 字节**（空市场）、`plugin_packages/` 目录**空**、服务端 state JSON 里
    **没有插件相关键**、访问日志里只有 App 在 `GET` 清单（156 条），**没有任何一次投稿 POST**
- **机制**：这个仓库的规律是"代码齐了但没接线的功能，真跑第一次必然掉东西"（FIX-07 三个扩展点、
  `logs` 接口、`clearMemory` 全是这么暴露的）。而这条链路横跨 App / 上传 / 审核 / 清单 / 安装五段。
- **改动**：以"我投一个真插件、走完审核、在 App 里装上"为目标跑一遍，把过程中撞到的问题逐条修掉
  （预计会撞到：审核状态流转、包体校验、清单缓存、安装后动作注册、下架）。
- **收益**：把一个对外功能从"没验证"变成"能用的"；也是插件生态能不能起来的前提。
- **成本**：1–2 天（按撞到的问题数）。
- **验收**：投稿 → 审核通过 → 清单里出现 → 另一个账户能安装并运行 → 下架后清单里消失；
  全程有服务端记录可查。

## 五、明确不做（沿用既有拍板）

- **不接宝塔面板 API**（面板 API 权限等同 root，把 key 放进客户端等于交出服务器）。
- **上传续传永不做**（WebDAV 无标准部分 PUT，带 `Content-Range` 的 PUT 会把文件覆盖成"这一段"= 静默损坏）。
- **`dart format` 不追**（仓库在该 formatter 下本就不干净，CI 只门禁 analyze + tests）。
- **不用宽泛 `pkill -f`**（会连自己的会话一起杀）。
- **175 清盘暂不做**（用户已定；磁盘 87%、现有 🟡/🔴 告警会盯着）。
