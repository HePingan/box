## 1. 第 1 组：低风险体检项（建议本轮全做）

四项都是"改动能看懂、风险有界、每项带测试"，互不依赖，可分别提交。

### D1. 大图缩略图：读 EXIF 内嵌缩略图（有界取前缀）

- **现状**：`models.dart:51` 把缩略图整取上限钉在 3MB，`models.dart:73` 超过即不取 → 你目录里 4.16MB / 10.6MB 两张只能显示通用图标（真机截图反馈）。
- **机制**：缩略图**必须完整文件才能解码**（JPEG/PNG 都要 IEND/EOI 之后才完整），所以"整取"的代价等于原图大小，3MB 上限正是被这个代价逼出来的。但手机/相机导出的 JPEG 一般在 EXIF APP1 段里**内嵌一张 160×120 左右的缩略图**（IFD1 的 `JPEGInterchangeFormat` / `JPEGInterchangeFormatLength`），**只要文件开头一小段**就能拿到并独立解码。
- **改动**：
  1. 新增 `domain/exif_thumbnail.dart`（纯逻辑、无 IO、无新依赖）：解析 `SOI → APP1/Exif → TIFF 头 → IFD0 → IFD1`，返回内嵌 JPEG 字节与 `Orientation`；对越界长度、非 JPEG、无 APP1 一律返回 null。
  2. `service.readThumbnail`（`remote_storage_service.dart:911`）改成两段式：`size ≤ kThumbnailMaxBytes` 走现有整取；否则用 `readUpTo(path, 256KB)`（`webdav_client.dart:316`，起点式 Range，**代价有界**）探 EXIF，命中就用内嵌缩略图，未命中回退通用图标（与今天行为一致，无回退风险）。
  3. `RemoteThumbnail` 无需改动（拿到的仍是"可解码的小图字节"）。
- **收益**：10.6MB 的相机照首次只花 ~256KB 就有缩略图；顺带把 `Orientation` 解析出来，为 0.2 节第 2 条（方向修正）留出免费的数据通道。
- **成本（粗估）**：约 0.5 天（解析器 ~120 行 + 真实 EXIF 样本字节的用例 + service 分支）。
- **验收标准**：
  - 单测：真实 EXIF 样本（相机原图前 256KB 的字节）解析出内嵌 JPEG；无 EXIF 的 JPEG / PNG 返回 null；长度字段越界不抛异常；`Orientation` 正确提取。
  - service 单测：大图只发**一次**有界 Range 请求（断言请求头与 `maxBytes`），且不落进缓存（未命中不缓存）。
  - 真机：坚果云相册里那两张 4.16MB / 10.6MB 是否出图（这是本项的最终判据，也会告诉我们 EXIF 命中率）。

### D2. 偏好持久化：排序字段 + 每目录滚动位置

- **现状**：`browser_page.dart:33` 的 `_sessionSortField` 与 `:155` 的 `_savedScrollOffsets` 都只在进程内有效（注释明说"不落盘"）→ 重启后排序回到"按修改时间"，长目录每次都要重新滚到底。
- **机制**：这两处状态没有落盘通道；而缩略图开关刚证明这个通道很便宜（`service.dart:942` → `store.loadThumbnailsEnabled`，SharedPreferences 一个布尔）。
- **改动**：`RemoteStorageStore` 加 `loadUiPrefs()` / `saveUiPrefs()`（排序字段 + `account|path → offset` 的 LRU 表，上限 200 条，坏数据静默丢弃）；页面 `initState` 读、变更时写（滚动写回做防抖，避免每帧写盘）。
- **收益**：用户偏好不再每次重置；进长目录回到上次位置（这本是移动端的基本预期）。
- **成本（粗估）**：约 0.5 天。
- **验收标准**：单测（存取往返、超限裁剪、坏 JSON 兜底）；widget 测试（构造时读到排序值并生效、滚动后写回被调用）。

### D3. 缩略图缓存收尾：占用可见 + 可清空

- **现状**：`clearThumbnailCache()`（`service.dart:939`）**全仓库零调用**——上一版加的 API 没有入口；用户既不知道缩略图占了多少空间，也无法回收。
- **机制**：磁盘缓存是"看不见的占用"，没有入口就不能解释空间去哪了，也违背"缓存必须可回收"的基本约定。
- **改动**：`RemoteThumbnailCache` 加 `Future<CacheUsage> usage()`（文件数 + 总字节，顺带复用 `prune` 的遍历）；顶栏「更多」菜单加一项「缩略图缓存：X MB」，点开显示"文件数 / 占用" + 「清空」（二次确认）。
- **收益**：32MB 上限的缓存从黑盒变成可观测、可回收。
- **成本（粗估）**：约 0.3 天。
- **验收标准**：单测（usage 统计正确、清空后归零、目录不存在时不抛）；widget 测试（菜单项显示占用、点击清空后 service 被调用）。

### D4. 传输队列：失败任务可重试

- **现状**：`TransferQueueSheet`（`page.dart:682`）活动任务有「取消」，失败任务只有一行"失败"文字（`:776-789`）；要重试只能回列表重新发起（下载能靠 `.part` 续上，上传得重新选文件）。
- **机制**：队列内部有重试计数与退避（`kTransferRetries = 2`，`models.dart:109`），但没有"把同一个任务重新入队"的公开方法。
- **改动**：`TransferQueue.retry(TransferTask)`（重置状态/进度/重试计数后重新入队，成功与活动中的任务不可重试）+ 任务行失败时显示「重试」。
- **收益**：弱网/弱 NAS 上的一次偶发失败不用把整套操作重做一遍。
- **成本（粗估）**：约 0.3 天。
- **验收标准**：单测（重试后真的重新执行、重试计数归零、已完成/进行中的任务拒绝重试）；widget 测试（失败行出现「重试」且点击后调用队列）。

## 2. 第 2 组：体验功能（拍板后做）

### D5. 图片预览左右切换（相册式）

- **现状**：`_ImagePreviewDialog`（`browser_page.dart:1557`）只接收单个 `entry`；弹窗内 `InteractiveViewer`（`:1617`）能缩放，但**没有上一张/下一张**，看相册要"点开-关闭-再点"。
- **机制**：预览弹窗与目录列表之间没有数据通道（只传了被点的那个条目），所以它无从知道兄弟文件。
- **改动**：把当前目录里的图片条目列表与起始下标传进弹窗，改用 `PageView` 承载；相邻页预取（复用缩略图缓存与 `readImagePreview`）；标题显示"3 / 17"；首尾边界不越界。
- **收益**：相册场景从"逐个点开"变成滑动浏览——这是照片目录里最高频的动作。
- **成本（粗估）**：约 1 天。
- **验收标准**：widget 测试（左右滑动切到下一张、标题计数、首尾不崩、只预取相邻页）；真机在坚果云相册连滑十几张。

### D6. 递归下载文件夹

- **现状**：多选「下载」明确拒绝文件夹（`browser_page.dart:315-326`），单项菜单也没有"下载文件夹"；服务层没有"列出子树"的能力。
- **机制**：下载路径只接受单个文件条目，`enqueueDownload` 一次一个文件。
- **改动**：service 加 `listTree(account, path, {maxDepth, maxEntries})`（BFS、**串行单连接**，避免把弱 NAS 打爆）；UI 在入队前先估算规模（"将下载 N 个文件，共 X MB"）再确认，超上限（如 2000 个文件）直接拒绝并说明；子目录按相对路径落到本地下载目录。
- **收益**：备份整个相册/目录一次完成（NAS 用户的核心动作）。
- **成本（粗估）**：约 1 天（含规模预估、上限保护、单目录失败不中断）。
- **验收标准**：单测（BFS 顺序、深度/条目上限、相对路径拼接、某个子目录失败不中断整体）；真机下一个小目录核对文件数与体积。

### D7. 目录列表离线快照（stale-while-revalidate）

- **现状**：目录缓存是内存态 15 秒（`service.dart:1007`/`:1013`）→ 冷启动/重启后进目录必须等一次完整 PROPFIND，大目录 + 弱网就是几秒空白。
- **机制**：列表只活在内存里，没有落盘。
- **改动**：把"最后一次成功列表"按 `account|path` 落盘（复用缩略图缓存那套：JSON + 条目/大小上限 + 修剪）；进目录先渲染快照（顶部标"正在刷新…"），后台请求回来再替换；**写路径的安全检查绝不使用快照**（沿用 O1/O3 的既有决定：冲突扫描必须实时）。
- **收益**：慢盘/弱网下"打开即见"。
- **成本（粗估）**：约 1 天。
- **验收标准**：单测（快照读写、过期判定、损坏兜底、写路径不吃快照）；widget 测试（有快照时先渲染 + 刷新后替换）；真机冷启动进大目录。

## 7. 待拍板（3 条）

1. **本轮范围**：建议**第 1 组全做 + D5**（相册滑动是照片目录里最高频动作），D6/D7 下轮。若只想先解决真机碰到的那件事，就只做 **D1**。
2. **大图策略**：只做 EXIF 探测（256KB 前缀），**不**顺带把 `kThumbnailMaxBytes` 从 3MB 提到 5MB——提高整取上限花的是你的流量，而 EXIF 路径能覆盖大多数相机照；若实测命中率低再回来讨论。
3. **D7（目录快照）**：建议本轮不做，等你真机确认"冷启动进目录要等好几秒"再排——它收益最大但也最容易引入"看到的是旧列表"的误解。
