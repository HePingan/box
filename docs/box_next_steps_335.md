## 二、组 1：低风险小改动（建议本轮，一版收口）

### A. 中转收口：撤掉临时令牌 + 关掉公网入口（服务与 App 侧代码都留着）

- **现状**：令牌库 `/root/.secrets/box-ops-api-tokens.json` 里仍有 `tmp-comic-relay`；边缘机
  `location ^~ /comicrelay/` 公网可达；`box-comic-relay.service` 在本机 active（127.0.0.1:8098）。
- **机制**：**没人用**（证据见事实基线 1）。留着 = 一个公网写口 + 一把长期有效的令牌 + 每周的告警噪音。
- **改动**：① 撤令牌 `box_ops_api.py token revoke --label tmp-comic-relay`；
  ② 边缘机注释掉 `location ^~ /comicrelay/` → `nginx -t && systemctl reload nginx`；
  ③ 书源的 `relay` 段与 App 侧代码**不动**（没配令牌就是直连，要恢复只需把 location 打回来）；
  ④ 在 `box-update-server` 技能里写明"恢复要哪两步"，免得半年后又被当成必需通道。
- **收益**：公网少一个入口、令牌库少一把长期令牌、告警静默；**App 行为零变化**。
- **成本**：约 0.5 小时，**不发版**。
- **验收**：撤令牌后带旧令牌请求 → `401`（负路径）；公网 `/comicrelay/fetch` → `404`（入口关了）；
  再跑一次源自检：野蛮漫画三步仍全绿（直连）。

### B. 更新包下载续传（断了不用重下 27MB）

- **现状**：`app_installer_io.dart:75` 只有 `onReceiveProgress`，没有 Range / `.part`；断一次从头再来。
- **机制**：手机切后台、切网络、信号差都会断（他自己报过一次"只能重新再次下载更新"）；而服务端
  **本来就支持续传** —— 实测 `box-1.20.78-335.apk` 返回 `accept-ranges: bytes`。
- **改动**：写 `<code>.apk.part` + 续传时带 `Range: bytes=<已收字节>-`；`ETag`/`Last-Modified` 与上次不一致
  就丢弃重下（防换包拼包）；收完后照旧 SHA-256 校验再改名（复用 `PendingUpdateApkStore` 的口径）。
- **收益**：27MB 断一次只补差额，弱网/切后台体感差别最大。
- **成本**：约 0.5 天，**要发版**。
- **验收**：单测（假 dio：中途断 → 第二次带 `Range` 且字节衔接；ETag 变了则重下）；
  真机：下载中关掉 Wi-Fi 再打开，进度从断点继续（**未验证项，需他看一眼**）。

### C. 漫画图片缓存纳入「清理缓存」+ 加上限/淘汰

- **现状**：`comic_image_cache.dart:42`（目录）、`:124`（`clear()` 零调用）、
  `personal_center_cache_service.dart:21-24`（清缓存不含它）、`data_settings_page.dart:78`（文案承诺清图片缓存）。
- **机制**：单话实测最多 209 张 × ~48KB ≈ 10MB，翻几本书就上百 MB，全落临时目录**且无上限**；
  用户在设置里点「清理缓存」，它不被清 —— 涨得最快的这一类清不掉。
- **改动**：① 加上限（如 300MB 或 2000 个文件），超出按 mtime 先删旧的；② `clearRegenerableCaches()`
  增加一步清 `comic_online_images`；③ 设置页把"当前占用"显示出来（清完归零）。
- **收益**：手机空间可控、文案与实际一致；顺带把零调用的 `clear()` 接上（悬挂 API 口径）。
- **成本**：约 0.5 天，**要发版**。
- **验收**：单测（超限淘汰最旧的、清缓存真的清了该目录；控制组：离线书 / 题库 / 登录信息不受影响）；
  真机：清缓存后再读会重新下载（预期行为）。

### D. 自检的搜索/详情也按 App 实际那条路（直连优先，WebView 兜底）

- **现状**：`comic_source_diagnostics.dart:178,278`（WebView）vs `comic_online_service.dart:258`（直连取文本 + 纯 Dart 规则引擎）。
- **机制**：两条路给的东西不保证一样，自检结论与 App 行为不同源；步骤 3 上周已对齐，1/2 还没对齐。
- **改动**：自检先跑直连（HTML 文本 + 规则引擎，**可离线单测**），拿不到卡片再退 WebView；
  每步说明里写清"这次走的是哪条路"（沿用 `lastPath` 那套口径）。
- **收益**：同一条结论既能在手机上验、也能在单测里锁；误报"源坏了"的最后一处隐患消掉。
- **成本**：约 0.5–1 天，**要发版**（可与 B/C/E 同批）。
- **验收**：假取数器造"直连通/WebView 不通"与"直连不通/WebView 通"两种组合，断言走了哪条路、结论与路线一致；
  控制组：直连失败时仍退 WebView，不把源判死。

### E. 出问题时在页面上就能去自检（入口放到失败态）

- **现状**：自检页入口只在漫画库（`comic_library_page.dart:206`）；在线页错误态只有重试（`grep 自检` 零命中）。
- **机制**：他只有手机。源出问题时最有用的一步是"跑一次自检、把结论复制回来"，而入口藏在另一页。
- **改动**：在线页错误态与书源菜单各加一条「自检这个源」，带上当前源直接进自检页。
- **收益**：报障时他能自己拿到证据（自检页已有「复制结论」）。
- **成本**：约 0.5 小时，**要发版**（与 B/C/D 同批）。
- **验收**：用例断言错误态的按钮进入自检页且选中当前源；控制组：正常态不出现这个按钮。

## 九、组 2 第一项落地：下一话预取 + 上一话/下一话 标签（1.20.80 / 337，2026-09-30）

### ① 顺手逮到的一个真 bug：两颗按钮标反了

`comic_online_page.dart` 里那条注释断言「目录是倒序的：index 大的更早」，于是左边那颗标着
**「下一话」**的按钮打开的是**上一话**（右边那颗「上一话」打开下一话）—— 两边的**标签与动作全反**。

判据不是读代码，是读真页面：`https://yemancomic.com/book/7530/` 的 HTML 里第 1 条是「1卷」、
最后一条是「第1193话」，**文档顺序 = 从早到晚**；规则引擎按文档顺序取卡片，所以 App 拿到的
`book.chapters` 是**正序**。修法：左边「上一话」= `index - 1`，右边「下一话」= `index + 1`，
并把那条错误的注释连证据一起改掉（注释不改，下一个人还会照旧前提再改回来）。

用例钉的是**请求**而不是字面（`FakeComicTarget.requests` = `opened` + `fetched`，看真碰了哪一话）：
点「下一话」→ 更晚那一话的地址；点「上一话」→ 更早那一话；第 1 话的「上一话」、最后一话的
「下一话」都**置灰**（`onPressed == null`）而不是乱跳。

### ② 预取下一话（`domain/comic_prefetch.dart`）
