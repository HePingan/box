## 一、问题一：小眼睛看不见 —— 真因已代码证实（**不是图标问题，是布局被裁**）

### 1.1 回读结论

| 检查项 | 实际代码 | 结论 |
|---|---|---|
| 眼睛图标本身 | `ic_eye_overlay.xml`，24dp 矢量，白色 0.95 alpha，路径完好 | **图标没问题** |
| 图标尺寸一致性 | 与 `ic_ai_vision_overlay` / `ic_region_overlay` / `ic_close_overlay` 同为 24dp | **无差异** |
| 按钮点击绑定 | `:1004` `btn_hide_overlay → toggleHiddenDot(view)` 正常 | **功能没问题** |
| 按钮可见性 | `:1481` 只调 `btn_quiz_entry`（考试态），**未给 `btn_hide_overlay` 设 GONE** | **未被主动隐藏** |

**→ 眼睛图标本身、颜色、尺寸、绑定全部正常。真因是标题栏宽度溢出被右侧裁切。**

### 1.2 溢出量化（真因）

标题栏 `title_bar` 是 `horizontal` 的 LinearLayout，子项顺序为：

```
[weight=1 拖动留白] → 相似度徽章(max 56dp) → 区域 → 录入 → AI读屏 → 眼睛 → 关闭
```

固定需求 = 徽章 56 + 5×(26+4) + paddingEnd 6 = **216dp**

而悬浮窗宽度（`defaultOverlaySize()` `:2992`）：

```kotlin
val w = (dm.widthPixels * 0.52f).toInt().coerceIn(280, 480)  // ← 注意：像素，不是 dp
```

| 机型 | 计算 | 悬浮窗宽 | 标题栏需求 | 结果 |
|---|---|---|---|---|
| 1080p (d=3.0) | 561px → clamp 480px | **160dp** | 216dp | **溢出 56dp** |
| 1080p (d=2.75) | 561px → clamp 480px | **175dp** | 216dp | **溢出 41dp** |
| 1440p (d=3.5) | 748px → clamp 480px | **137dp** | 216dp | **溢出 79dp** |

**结论：所有真机上标题栏都装不下，最右侧的「眼睛」和「关闭」被裁掉。** 截图里工具栏右端硬切正是此现象。

**引入时点**：AI 读屏按钮（`btn_ai_vision`）是我上一轮加的动作簇第 4 项，把它从 4 个按钮撑到 5 个按钮，直接触发本回归。**这是我引入的缺陷。**

### 1.3 方案（按收益/风险分级）

**A 档（低风险，推荐先做）**
- **A1. 把眼睛移出标题栏，改为「缩成小圆点」的常驻入口**：`hidden_dot` 已存在且已绑定（`:1004`/`:1554`），当前却只能从眼睛按钮进入 → 自相矛盾（要隐藏得先找到看不见的按钮）。把「隐藏」动作改挂到**长按关闭**或**标题栏双击**，眼睛按钮即可从标题栏删除，省 30dp。
- **A2. 徽章 `maxWidth` 从 56dp 降到 40dp**，省 16dp。
- **A3. 按钮规格统一收紧**：26dp→24dp、marginEnd 4dp→2dp，5 个按钮省 **30dp**。

A1+A2+A3 合计省 **76dp** → 标题栏需求降到 140dp，**在当前所有机型都装得下**。

**B 档（中风险）**
- **B1. 让标题栏随内容自适应**：`defaultOverlaySize` 的 `coerceIn(280,480)` 改为按**最小内容宽度**求下界（至少 216dp×density），保证永不裁切。代价：悬浮窗变宽，遮挡题目区域更多 —— 与既有「紧凑 5:4 卡片」的刻意设计冲突，**需要你拍板取舍**。
- **B2. 动作簇收进「更多」溢出菜单**：仅保留 AI 读屏 + 关闭在标题栏，其余进 `btn_more` 弹出层。代价：多一次点击。

**C 档（过渡兜底）**
- C1. 标题栏 `HorizontalScrollView` 包裹，可横向滑动。代价：悬浮窗内横向滚动体验差，不推荐。

### 1.4 我的建议

**A1+A2+A3**：零取舍、纯收益、不动悬浮窗尺寸。眼睛按钮从标题栏消失的同时，「隐藏为小圆点」改为长按关闭触发（可发现性反而更高），「关闭」留在最右。

## 一·补：用户追加诉求 —— 顶层只放功能按钮，相似度移走

### 1.5 现状（回读证实）

标题栏 `title_bar` 当前混装「状态徽章 + 5 个功能按钮」：

```
[weight=1 拖动留白] → tv_title(相似度徽章 56dp) → 区域 → 录入 → AI读屏 → 眼睛 → 关闭
```

- 相似度**只在标题栏徽章显示**（`:137` 注释确认摘要条已移除，`status_bar` 仅是 3dp 色条）
- 徽章文案唯一写入点：`:3160` `badgeText`；另 `:1269` 读屏期临时改「读屏中」
- 徽章与按钮**抢同一行宽度** → 这正是眼睛被裁的直接原因

### 1.6 方案：相似度从标题栏迁到「题目区顶部」

**不动核心设计**（`:137` 已明确"相似度只在标题显示，避免重复占高"），因此**不新增整行**，而是：

**推荐 A：迁到题目区左侧内联**
- 在 `scroll_question` 上方/内部左侧放一个窄徽章（40dp 内），与题干首行同高
- 标题栏只剩纯功能按钮 → 一行装得下，眼睛不再被裁
- 优点：不加高度；缺点：长题干换行时需处理对齐

**推荐 B：迁到状态色条 `status_bar` 上**
- 把 3dp 纯色条升级为「3dp 色条 + 右侧 20dp 高的小徽章」，或直接让色条本身按相似度着色并在末端显示数字
- 优点：完全独立一行，零挤压；缺点：`status_bar` 只有 3dp 高，需撑到 18-20dp（约多占 15dp 高度）

**推荐 C：降级为「仅在结果区顶部显示一次」**
- 相似度并入答案区第一行（如「答案：C ｜ 相似度 100%」）
- 优点：标题栏彻底解放；缺点：与既有"正文只显示答案本身"的约定冲突

### 1.7 与 1.3/1.4 的关系

若采纳 1.6，则 1.3 的 A2（缩徽章至 40dp）可**直接取消** —— 徽章根本不在标题栏了，标题栏需求从 216dp 降到
`5×(26+4) + 6 = 156dp`；再叠加 A3（按钮 24dp/margin 2dp）→ **130dp**，全部机型富余。

## 二、问题二：大模型搜题进度及提示

### 2.1 现状回读

已有基础（上一轮做的）：
- `markVisionRunning(root, true)`（`:1261`）：徽章改「读屏中」+ 正文改「AI 读屏中…（最长约 45 秒，请稍候）」+ 按钮禁用置灰
- `overlayStatus="searching"` → 状态条橙色 `0xFFF59E0B`
- 结果回来由 `updateOverlay` 汇聚点复位

**缺口（对照你的诉求）**：
1. **无进度感** —— 文案是静态的「最长约 45 秒」，**没有已等待时长、没有阶段、没有转圈动画**。用户盯着一个不动的字等 45 秒，体验等于卡死。
2. **无阶段提示** —— 重试链（2s/5s/10s/15s 退避）对用户完全不可见，第 2 次重试时用户不知道还在跑。
3. **无失败归因细化** —— `_visionFailureHint` 在 Dart 侧有，但悬浮窗正文只显示一句话，用户看不到「是网络问题还是模型没读出题目」。

### 2.2 方案（按收益/风险分级）

**A 档（低风险，推荐）**
- **A1. 徽章倒计时**：`markVisionRunning` 后启动 `Handler` 每 1s 更新徽章为「读屏 12s」，让"还活着"可见。结果/失败时 `removeCallbacksAndMessages` 停表。
- **A2. 正文分阶段文案**：按已等待时长切三档 ——
  - `0-3s`：「正在截图并识别题目…」
  - `3-15s`：「正在请求大模型（首次较慢）…」
  - `>15s`：「仍在重试（网络波动，最长 45 秒）…」
- **A3. 进度条**：`status_bar` 下方加 2dp 不定型 `ProgressBar`（`indeterminateTint` 跟随状态色），跑动感。
- **A4. 按钮 spinner**：AI 按钮在跑时换成小转圈（或 alpha 脉动动画），替代当前"单纯置灰"。

**B 档（中风险）**
- **B1. 真实阶段上报**：Dart 侧在每个阶段（截图→压缩→请求→重试 n）回调 Kotlin 更新文案，进度真实而非按时长猜。需新增 native method channel（**当前 native 侧无 method handler，只有单向 Dart→Kotlin**，见前序结论），成本较高。
- **B2. 可取消**：跑动期间再点 AI 按钮 = 取消当前请求。需要请求侧支持取消。

**C 档**
- C1. 悬浮窗内显示已用 token / 已耗时明细，偏工程化，价值有限。

### 2.3 我的建议

**A1+A2+A3+A4**：全部是 Kotlin 侧自足改动，不新增 channel，不动 Dart，**不依赖后端**。倒计时+分阶段文案+转圈，足以解决"以为没反应"的核心焦虑。
