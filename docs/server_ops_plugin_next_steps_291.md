# 服务器运维插件（server_ops）下一步优化方案

线上基线：**1.20.34 (291)**。插件已内置（三页签：服务器 / 文件 / 终端），且已是**多服务器模型**
（设置里服务器列表 + 顶部切换器，口令按机器分键、只存本机加密存储）。
本方案基于 **291 的代码 + 2026-09-25 对运维通道的第二轮真实探测**，行号均已回读核对。

上一份是 `docs/server_ops_plugin_next_steps_289.md`（A1–A8 / B1 客户端+服务端 / C1 两档均已落地，
见它第七节）。**本文只写它没有的、以及它列而未做的**，不重复已否决项。

### 1.2 文件通道暴露的密钥（**这一条决定了本轮的排序**）

任一 ops 口令 + 一条 `curl` 就能把发布链的根材料下载走（下表是**只读探测**的真实返回，
不打印内容）：

| 通道 | 路径 | 结果 |
|---|---|---|
| `/dav175` | `root/.secrets/box-release.p12`（**APK 发布签名库**） | `200`，4402 B |
| `/dav175` | `root/.secrets/box-release-keystore-password` | `200`，28 B |
| `/dav175` | `root/.secrets/box-update-manifest-sign-secret` | `200`，65 B |
| `/dav175` | `root/.secrets/box-ops-webdav.password`（**主服务端那只口令**） | `200`，48 B |
| `/dav175` | `root/.ssh/hermes-target`（**连 hpa888 的私钥**） | `200`，399 B |
| `/dav175` | `root/.ssh/id_ed25519` | `200`，432 B |
| `/dav` | `root/.secrets/box-update-server.admin_password` | `200`，12 B |
| `/dav` | `root/.secrets/box-update-manifest-sign-secret` | `200`，65 B |
| `/dav` | `root/.secrets/box-update-server.env` | `200`，637 B |
| `/dav` | `etc/shadow` | `200`，1029 B |

复现（只报状态码与字节数，不落内容）：

```bash
PW=$(cat /root/.secrets/box-ops175-webdav.password)
curl -s -o /dev/null -w '%{http_code} %{size_download} B\n' \
  -u "boxops:$PW" https://box.hpa888.top/dav175/root/.secrets/box-release.p12
```

**为什么这是最高优先级**：拿到签名库 + 签名库口令 + 清单签名密钥，就能**签一个假的 APK
发给我们全部用户**（客户端验签会通过）——整条发布链失守。而 175 那条口令还顺带给出
**主服务端口令与 SSH 私钥**，等于两台的密钥互开。App 侧**根本不需要**这些文件，
它们之所以可达，只是因为我们把 `/` 整个 serve 了出去。

**边界要说清**：终端本来就是 root shell（口令 = root），所以这不是"口令泄露后多了一条路"，
而是**意外暴露面**变大了 —— 手机上的文件浏览器会把密钥下载到手机（缓存/备份落在比服务器弱的
设备上）、共享屏幕时列表一划就露出来。黑名单收口能消掉这一类，但**它不是安全边界**；
真正的边界是下面的 C2（设备令牌 + 路径白名单 + 审计 + 可撤销）。

### 1.3 大目录的代价（复现）

```bash
PW=$(cat /root/.secrets/box-ops-webdav.password)
curl -s -u "boxops:$PW" -X PROPFIND -H 'Depth: 1' \
  https://box.hpa888.top/dav/usr/lib64/ -o /tmp/pf.xml -w '%{size_download} B %{time_total}s\n'
```

`485174 B / 30.49 s`。同法测得 `/etc` 132 KB / 1.32 s（235 项）、`/root` 154 KB / 1.32 s（257 项）。
线上 175 的磁盘用到 77.8%，这种目录并不罕见。

## 二、路线分组（顺序即执行顺序）

### A 组：低风险体检项（一发就能感知，互不重叠）

**A9. 真机反馈闭环：体检面板加"最近一次真实请求"**

- 现状：体检（`server_ops_diagnostics.dart:84` 的 401 文案、`server_ops_page.dart:629` 的
  防呆）只在**点测试时**给结论；用户真机上传/下载/终端出问题时，截图里只有一句报错，
  哪台机器、哪个入口、什么状态码、耗时多少全都没有 —— 289 列的三个"必须真机"项就是这样一轮轮顺延的。
- 机制：请求的元数据（入口 / 机器 id / 状态码 / 耗时 / 时间）在服务层都能拿到，只是没人记；
  口令不在其中（只记状态码，不记请求头）。
- 改动：运行期维护一个**最近 20 条请求元数据**的内存环形缓冲（可选落盘），体检面板底部渲染
  成一张小表；每条含入口、机器、状态码、耗时、相对时间。
- 收益：把"说不清"变成"截图自带证据"——下次真机反馈我不用再问"你当时填的是哪台"。
- 成本：0.5 天。验收：单测断言元数据不含口令字段、环形缓冲只留 20 条、失败项状态码正确。

**A10. 一键接入补齐"指标"这一半（新机器不再只有文件与终端）**

- 现状：`tool/box_ops_provision.sh` 装出的是 rclone + ttyd + 隧道 + 凭据（实测全绿），
  但**没有把新机器接进采集器**：机器清单是 `tool/gen_hosts_json.py:39-40` 里手写的两条，
  接入脚本对它的命中是 0（只有 nginx 那个 `/hosts.json` 锚点）。结果是新机器在
  「服务器」页**永远不出现**，而文件/终端却是通的 —— 一半接好了，用户会以为"没接成功"。
- 机制：采集器在 175 上跑（cron `*/2`），按清单里的 `ssh` 别名去取远程指标，
  加机器 = 改清单 + 部署 + 校验 `hosts.json` 出现该 id。
- 改动：接入脚本增加 `--metrics` 段（默认开）：把新机器写进清单（id/name/ip/ssh 别名）、
  部署采集器、跑一次 `--collect`、断言 `hosts.json` 里出现该机器且 `status=online`；
  失败只告警不阻断（指标不是文件/终端的前置条件）。
- 收益：接入一台机器 = 一条命令，三件（文件/终端/指标）都齐。
- 成本：0.5–1 天。验收：拿第三台机器（或 `--dry-run`）跑一遍，`hosts.json` 里断言命中该 id。

**A11. 大目录：条目上限 + 继续加载**

- 现状：`PROPFIND Depth:1` 一次拿全量（1.5 节实测：1500 项要 30 秒、485 KB），
  页面在这 30 秒里没有进度、没有取消、也没有"这目录很大"的提示（`files_tab.dart` 无条目上限）。
- 机制：`--dir-cache-time 0` 是刚需（否则新上传的文件看不见），所以**服务端这条路的成本降不下来**，
  只能在客户端把体验做对：先渲染前 N 项 + 「还有 M 项，继续加载」。
- 改动：列表默认渲染 300 项，超过则底部给「继续加载」；请求中显示"正在列举（大目录可能较慢）"，
  带取消；服务端错误与超时文案区分开。
- 收益：`/usr/lib64` 这种目录不再表现为"App 卡死"。
- 成本：0.5–1 天。验收：假服务返回 2000 项时只渲染 300、点「继续加载」后 600，取消后不再 setState。

**A12. 大文件传输的续传与重试提示**

- 现状：无 `Range`（1.6 节），传输中断只能从头来；失败文案没有说明"重来会不会覆盖"。
- 机制：服务端 `Range` 支持 `206` ✅（下载可用）；上传的续传要看 rclone 对 `Content-Range` 的支持，
  **这一条必须先探测再承诺**（探测方法与"服务端可能不合规"的纪律见技能
  `references/webdav-server-quirks.md`）。
- 改动：下载走 Range 断点续传（写临时分片 + 校验大小后改名）；上传若探测不支持续传，
  就只做"失败重试 + 明确提示会从头重传"，并把探测结论写进本文档。
- 收益：几十 MB 的日志/备份包不再因为一次掉线全丢。
- 成本：1 天（含上传侧探测）。验收：live 用例断言 Range 续传后文件大小/内容一致；上传侧给出探测结论。

**A13. 把 server_ops 纳入悬挂 API 闸门**

- 现状：`tool/scan_dangling_apis.py` 只扫 `remote_storage` + `monitor`（1.1 节第 2 条）。
- 机制：该脚本已经支持多目录（`ALLOW` 白名单也在），只是没把新插件加进去。
- 改动：扫描目录加 `lib/features/extensions/plugins/server_ops`，逐条判定白名单里的是"接线"还是"删掉"。
- 收益：这个 5976 行的插件以后也有"写了没用"的守卫。
- 成本：0.25 天。验收：`python3 tool/scan_dangling_apis.py` 覆盖三个插件目录且悬挂 0。

**B2. 主机历史服务端化**（289 原文照搬，未做）

- 现状：折线历史是客户端环形缓冲，装上才开始攒、换设备就没了。

### C 组：安全 / 服务端（要动安全模型或上服务端组件，单独立项）

**C4. 运维通道暴露面收口（本轮最高优先级，0.5 天）**

- 现状：两条通道 `rclone serve webdav /`（1.1 节第 4 条），密钥类文件全部可达（1.2 节实测）。
- 机制：我们 serve 的是整盘，而"整盘"里就放着发布链的根材料；App 一行代码都没用到它们。
- 改动（黑名单形态，最小改动）：两条 `ExecStart` 加过滤 —— 密钥目录、私钥目录、签名库后缀、
  `box-*.env`、`/etc/shadow`：
  `--exclude "/root/.secrets/**" --exclude "/root/.ssh/**" --exclude "*.p12" \
   --exclude "*.env" --exclude "/etc/shadow"`（rclone `serve` 自带 Filter 组，已实测可靠）；
  `tool/box_ops_provision.sh` 同步生成同样的过滤（新机器默认就收好）；
  改完 `systemctl restart` + **live 用例断言这些路径 404、而 `/root`、`/etc` 的普通文件仍 200**。
- 收益：钥匙不再被"看一眼/划一下"就带走；把"口令泄露 = 立刻拿到签名库"降级成"还要过终端那关"。
- 成本：0.5 天。验收：live 用例覆盖上表 10 条路径（全 404）+ 3 条对照路径（全 200）；
  两条通道都要测（175 与 hpa888 的过滤各自生效）。
- **诚实边界**：黑名单挡不住有口令的人 —— 终端仍是 root，`cat` 一下就回来了。
  它消掉的是"文件通道 + 手机缓存/备份/截屏"这一类的意外暴露；真正的边界是 C2。

**C2. 服务端受限执行 API（宝塔式能力的唯一前提；建议分两档）**

> **只读档已完成（2026-09-25）**：`tool/ops_api/box_ops_api.py`（纯标准库、白名单只读动作、
> 设备令牌、全量审计）+ `deploy_box_ops_api.sh` + 客户端第四个页签「系统」。
> 落点与边界见 `docs/ops_channel_20260925.md` 第十三节。**写档仍未做**（有意：等审计与令牌先跑一段）。

- 现状：WebDAV 拿不到 unix 权限/属主，也没有进程、服务、日志、解压、目录大小 —— 289 已实测，
  结论不变。要做这些必须先有一个**服务端执行通道**。
- 机制：一个小的 FastAPI 服务（可复用 `box-update-server` 的骨架与既有运维约定），
  只暴露**白名单动作**，全部落审计；App 不带 root 口令，带的是**设备令牌**。
- 改动分两档（**建议先只读档**）：
  - **只读档（1.5–2 天）**：进程列表 / 服务状态 / 日志 tail（限行数）/ 目录占用 / 端口监听 /
    登录记录摘要。全部是"看"，风险最低，但已经覆盖日常排障的八成。
  - **写档（再 1.5–2 天）**：服务启停重启 / 解压 / chmod。写档必须等设备令牌与审计先落地，
    否则等于把 root 换个壳又开放一次。
- 收益：插件从"文件管理器 + 终端"变成"服务器面板"；同时它是 C1 根治档与 C3 的载体。
- 成本：见两档。验收：白名单外一律拒绝且有审计记录；每类动作一条 live 用例；
  审计能用 `GET /audit` 按设备/动作查回来。

**C3. 阈值告警推到飞书**（289 原文照搬，未做）

- 现状：只有人打开 App 才看到指标（与既有 Kuma/Feishu 告警是两条线）。
- 改动：175 采集时判阈值（CPU/内存/磁盘/离线/关键服务 down），经现有 Feishu 通道推送，带静默期。
- 成本：1 天。验收：造一次假阈值触发，飞书收到且不重复轰炸。

**C1 根治档（承接 289 的三档模型）**

- 现状：立即档（轮换脚本 + 风险告知）与中期档（包内不再有口令、本机 Keystore）**已完成**。
- 改动：根治档 = 设备令牌 + 路径白名单 + 审计 + 可撤销，**与 C2 同一件事的两面**，绑定做。
- 成本：含在 C2 里。验收：撤销一台设备令牌后该设备立即失效，其余设备不受影响。

## 三、明确不做

| 不做 | 理由 |
|---|---|
| 接宝塔面板 API | 权限等同 root（写任意文件 + 执行命令），key 进 APK 即失守；289 已否决，不重开 |
| 把文件通道收成"白名单目录" | 会破坏你明确要的"整个盘"；白名单形态留给 C2 的路径白名单去做 |
| 给文件通道加设备双向认证/TLS 客户端证书 | 与 C2 的设备令牌重复，别在 rclone 这条路上叠一层半成品 |
| 权限/属主列 + chmod/chown | WebDAV 不返回该属性（实测）；C2 只读档也不做，留到写档 |
| 文件列表缩略图 | 远端缩略图要整图下载，几百张图狂吃流量；除非 C2 提供服务端缩略图 |
| 客户端打包/解压后上传 | 大包要过手机上行；服务端解压属 C2 写档 |
| 把 `/term/` 换成非 root 用户 | 你明确要 root shell；改这个等于改需求，风险写在 C1 |
| PHP / 网站 / 数据库 / 防火墙管理 | 不是这两台机器的场景 |

### A10 实测（含自检当场抓到的两个自造坑）

`tool/box_ops_monitor_add.sh` 走"监控机发起"的方向（要往目标机 `authorized_keys` 装监控机的专用钥匙），
与接入脚本的信任方向相反。自检用真实机器跑了完整闭环：

* 装：`t99test`（借 `ssh hpa888` 当目标）→ 采集输出里**出现第 3 台且 online=True**；
* 拆：清单条目 / `~/.ssh/config` 的 `boxmon-<id>` 段 / 目标机 `authorized_keys` 里那行 —— **残留全 0**；
* 不污染线上：自检用 `BOX_OPS_HOSTS_OUT` + `--no-push`，线上快照始终是那两台。
* 自检抓到的两个自造坑（都已在脚本里修 + 加了前置校验）：① 条目被插到 `EXTRA_HOSTS = [...]`
  的**右括号之后**（标记包住了整条声明），采集器直接 `IndentationError`；② `--remove` 摘公钥用
  `$MARKER-$ID` 去匹配，而密钥注释是 `$MARKER` —— 一行都没摘掉却报告成功，现改为**按公钥指纹匹配**。
